## Defect — Frontend: Graphics "MToon Shading" toggle could not be turned off (P2)

material as `MToonMaterial`); the toggle only overrode `shadingShiftFactor`
(0.85) and `shadeColorFactor` (`#1a1020`) in `RendererSetup.tsx`. Label and
description ("Anime-style toon shading") described something always true.

  "on" (never re-stashes overridden values), restores and clears on "off".
  Mutates the uniform's Color in place (`.set` / `.copy`). 6 tests (on, colour
  override, off-after-on restores, on-twice keeps original, off-untouched,
  non-MToon ignored).
- `RendererSetup.tsx` uses it.
- `environmentConfig.ts` `mtoon.shadeColorHex` → `null` (keep each model's
  authored shadow tint; the shared near-black made skin shadows muddy).
- Relabelled (key `mtoon` kept so saved settings still apply): en "Softer
  shadows" / "Smaller shadow areas on the character"; vi "Bóng đổ mềm hơn" /
  "Thu nhỏ vùng bóng tối trên nhân vật".

## Feature — Frontend: facial track for the kiss gesture

**Ask (Owner):** give the kiss a matching face, to test that the face mesh
works as intended (before reply-driven emotion).

**Before:** clicking the mouth played Kiss.fbx + `happy` for 600 ms; the face
never puckered or closed its eyes. `AnimationStates.gesture.facial.hold` was
defined but never read (still unused; the face track supersedes it).

**Design:** data-driven, per character, in the profile next to the gesture.
- `AvatarProfile.GestureDef.face?: FaceKey[]` — keyframes `{ t, face }` in the
  profile's vocabulary (`FaceToken` = canonical emotion | viseme A–O | `blink` |
  `blinkLeft` / `blinkRight`), resolved per model (recipes / visemes /
  blinkChannel), so one track works on every character incl. Bronya's repaired
  channels and her custom `Surprised`.
- `avatar/GestureFaceController.ts` — new mixer contributor, LAST (after
  blink). While active it owns the track's channels + all viseme channels + the
  blink channel (lip-sync cannot hold the jaw open through a pucker, auto-blink
  cannot pop the eyes open). Smoothstep between keys; blended over the lower
  layers with a 0.15 s fade-in / 0.25 s fade-out envelope; `stop()` fades out
  early. `faceTrackChannels()` feeds `VRMExpressionAdapter`'s managed set
  (unmanaged channels are never written).
- `AvatarController.playFaceTrack / stopFaceTrack` (engages for the track's
  length so the idle wanderer stays out). `ActivityDispatcher` starts the track
  after `transitionTo('gesture')` resolves (clip loaded and playing), only if the
  same avatar is still attached. `MotionContext` stops it when the FSM leaves
  `gesture`.
- Kiss track (`profiles/default.ts`, clip 3.73 s, hand nearest ~1.9 s):
  0 {} → 0.5 happy .4 → 1.1 happy .15 + U .5 → 1.5–2.2 U .9 + blink .9 →
  2.6 happy .6 + U .1 → 3.4 happy .4 → 3.73 {}. `happy` is 0 while the eyes are
  closed (some models' happy blocks blink/mouth); full `blink` rather than a
  wink because Bronya has no working blinkLeft/Right.
- Dev handle: `__fsm.face('<channel>')` returns the live composed weight.

**Tests (red first):** `GestureFaceController.test.ts` 11 (resolution incl.
Bronya, managed-channel list, keyframe values, overrides lip-sync/blink,
leaves foreign channels, fade-in without snap, self-ends and hands back,
stop fades, degenerate tracks ignored); `ActivityDispatcher.test.ts` +3 (face
starts after the clip, not when the FSM refuses, gestures without a face leave
it alone). `tsc` 0, `eslint` clean, `vitest` 33 files / 359 tests.
**Not seen on a real avatar** (Cognito + CDN models). Known limit: the track
runs on wall-clock time, so the dev playback-speed slider (≠ 1×) desyncs it.

## Feature — Reply-driven avatar emotion (backend + frontend)

**Ask (Owner):** after the kiss face checked out, make the avatar's expression
follow the tone of each reply.

**Flow:** synthesizer prompt asks for one leading tag `[emotion: NAME N]` →
stripped from the stream as it arrives → sent as its own custom-stream item →
`api/main.py` emits SSE `emotion` → `ChatContext` validates and calls
`AvatarController.setEmotion`. Same LLM call, a few output tokens, emotion
arrives BEFORE the text.

**Backend — `shared/reply_emotion.py` (new):**
- `PROMPT_RULE` appended LAST to the voice card (instructions nearest the
  generation point are followed most reliably). Vocabulary: neutral, happy,
  sad, relaxed, surprised (no angry). `VVA_REPLY_EMOTION=0` removes it.
- `parse_emotion_tag` — tolerant regex (`:`/`=`, `,`/space, any case,
  whitespace); a well-formed tag is always removed even if its emotion is
  unknown; `[1] …` and other brackets left alone.
- `EmotionTagStream` — holds back only while the start could still be the tag
  (≤ 48 chars, prefix of `[emotion`), so text flows immediately otherwise;
  handles the tag split across any number of chunks and trims the space after
  it even when that arrives in the next chunk (a real bug the tests caught).
- `apply_emotion_policy` — refuse mode or `red_flag_screen` /
  `referral_advice` → neutral; angry → neutral; caps happy .8, sad .5 (reads
  as sympathy), relaxed .8, surprised .6; floor .1.
- `nodes/synthesizer.py` — streaming loop routes chunks through the tag
  stream (`final` = clean text only → history, TTS, grader never see the tag);
  flush at end; non-streaming and Gemini-fallback paths parse the full text.
- `api/main.py` — custom payload `{"emotion": …}` → `encode_event("emotion")`.

**Frontend:** `lib/replyEmotion.ts` `parseReplyEmotion` (canonical names only,
intensity clamped, default .6, anything else dropped) + `REPLY_EMOTION_FADE_MS`
700; `ChatContext` handles `emotion`, and calls `avatar.notifyEngaged()` on each
token so the expression holds while the text streams (without it the idle
wanderer took over 3 s after the event, mid-reply).

**Tests:** backend `test_reply_emotion.py` 23 (parser formats, stream splits,
brackets, flush, policy; synthesizer: emotion first + clean text + clean
final_answer, safety → neutral, no tag → no event, fallback cleaned,
non-streaming cleaned, prompt present / switched off) — written red first.
Frontend `replyEmotion.test.ts` 4. Frontend `vitest` 34 files / 363, `tsc` 0,
`eslint` clean (1 pre-existing warning).

**Real-model check** (live synthesizer, persona Miki, vi): greeting → happy
.6; low-back pain → sad .4; shoulder stretch guidance → relaxed .5; chest pain
+ `red_flag_screen` → neutral (policy). Tag absent from streamed and saved text
in all four.

**Backend suite:** 675 passed, 34 errors (moto, as before), 1 failed —
`test_phase6_circuit_breaker::test_planner_degrades_when_no_provider_can_be_built`
fails identically WITHOUT these changes: it deletes the DeepSeek key but this
machine's `.env` has a Gemini fallback key, so a provider can still be built.
Passes in CI (no `.env`). Pre-existing, local-environment only.

**Not done (follow-ups):** per-sentence emotions timed to TTS; per-character
emotion guidance in persona `.md`; a tag written mid-reply (not at the start)
is not stripped from text already streamed.

## Fix — Frontend: kiss camera aimed at the chin and went through the avatar

**Owner:** the locked kiss camera should sit close to the NOSE; it framed the
chin/mouth, and the lens passed through the avatar during the clip (Mixamo
"Kiss" has a slight up-heel).

**Measured on Kiss.fbx** (Node + FBXLoader + AnimationMixer, Mixamo skeleton,
metres): head moves **26.1 cm forward** and **7.8 cm up**; heel lifts
**8.6 cm**; the right hand swings to **63 cm in front of the nose** (off-axis)
at ~0.97 s. With the old camera HELD in front of the face, the closest joint
came to **17.1 cm** (2.10 s) — the mesh extends ~10 cm past joints, so the
0.1 m near plane was inside her.

**Causes:** (1) aim point = head bone (≈ jaw height) pulled 40 % toward the
kissing hand → chin/mouth framing; (2) `holdPosition` froze the camera while
the avatar leaned 26 cm into it.

**Fix:**
- `lib/faceLock.ts` — `noseFocus` (eye-bone midpoint − 3 cm, else head bone +
  7 cm) and `clearanceBackoff` (extra distance along the view direction so all
  joints ≥ clearance; bounded at 1 m). 7 tests, red first.
- `CharacterViewer.tsx` — `CameraModeDef.holdPosition` → `focus: 'nose'` +
  `followFace`: every frame the camera is PLACED at the preset offset from the
  nose (moves with the lean / up-heel), target damped toward the nose; no hand
  pull. Backstop `FACE_CLEARANCE` 0.2 m over all humanoid bones: backs off
  instantly, eases back (rate 3/s). Runs regardless of `followTarget` (lock owns
  the camera). Face preset `[0, 0.6, 0]` (mobile `[0, 1.0, 0]`, target −0.15).
- Simulated with the same rule on the clip: at 0.6 m from the nose, following
  it, the closest joint is **24.1 cm** and the backstop never triggers (probe
  alternatives: 30 cm backstop alone needed up to 34 cm back-off with 8–10 cm
  per-frame jumps — rejected as jerky).
- Release ease-out after the kiss unchanged (pre-lock view is anchored to the
  head bone on both sides).

**Supersedes** the 25/09 "track the kissing hand" behaviour (Owner now wants a
nose lock); the camera still moves — with the face, not toward the hand.
`trackBone`/`trackWeight` remain available in `CameraModeDef`.

`tsc` 0, `eslint` clean, `vitest` 35 files / 370 tests. Not seen with a real
VRM (Cognito); the simulation is on the Mixamo skeleton, before retargeting.

## Kiss partner POV — camera went inside her head (fix)

**Report (Owner):** during the second half of the kiss the camera entered the avatar's head; "zoom, but not that much".

**Cause:** the partner point was the nose/palm midpoint, ~13 cm from the *nose point*. That point is derived from the eye bones, so it lies inside the head, and the VRM anime head (plus hair) extends well past 13 cm. The only guard during the shot was 8 cm, and the joint backstop is off while the shot plays.

**Fix:**
- `faceLock.ts`: `PARTNER_MIN_DISTANCE` 0.12 → **0.28**.
- `CharacterViewer.tsx`: `PARTNER_FACE_GUARD` 0.08 → **0.22**, the same as `FACE_CLEARANCE` for the head. As she leans in 26 cm, the frozen camera backs off to keep at least this distance.

**Checked on the Kiss.fbx numbers:**
- The camera sits 28 cm from the nose point.
- The resting left palm is 7 cm beside the lens and 77° off-axis, outside the 30° half-FOV, so it stays out of frame (a hand around the viewer's head, not over the lens).

**Tests:** faceLock tests updated; vitest 36 files / 392 tests pass, tsc 0, eslint clean.

**To tune:** if the close-up is still too tight or too loose, change only `PARTNER_MIN_DISTANCE` (and keep the guard at or below it).
