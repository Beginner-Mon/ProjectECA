# Worklog 19/09/2026 — Motion playback failure was silent on one test laptop

## Context

Branch `local-testing-improve` cut from `origin/release` (`e4c383a`) — the
most-ahead branch at the time (`feature/langgraph-rewrite` was 53 commits
behind it). Not pushed.

Four-laptop test: three played the Kimodo motion, one did not, and the
failure survived a page refresh and a new chat session. Shared backend
causes (dead `worker#heartbeat`, `busy` queue, planner `needs_motion=false`)
are transient and would have hit all four, so the cause is per-machine or
per-account. Root cause not yet confirmed — see "Evidence still needed".

## Defect — Frontend: `playMotionFile` result dropped (P1)

**Symptom:** user sees `motion_rendering` ("Building the movement..."), then
the notice clears with no clip and no error.

**Cause:** [[ChatContext]] `motion` SSE handler awaited `playMotionFile()` but
never read its boolean. That function returns `false` (never throws) when:

- the avatar has no controller/registry — WebGL off, GPU blocklisted, VRM
  never attached (`MotionContext.tsx:278`);
- the clip failed to fetch or retarget — `AnimationRegistry.build()` catches
  and returns `null` (`AnimationRegistry.ts:88`), e.g. CloudFront blocked
  by proxy/ad-blocker, or a character with `incompatible_reasons`;
- the FSM refused the transition or the controller was disposed mid-switch.

Every one of those ended with `notice(undefined)`, indistinguishable from
success.

**Fix:** `ECA_UI/frontend/src/contexts/ChatContext.tsx` — check the return
value; on `false` log `[motion] avatar could not play clip` with the job id
and set `copy.motion_failed` on the message.

**Verification:** `vitest run` 285/285 pass. `tsc --noEmit` error count
unchanged at 27 before/after, all pre-existing (`i18next`,
`react-i18next`, `i18next-browser-languagedetector` not in `node_modules`
on this machine; two implicit-any in `AvatarsPanel.tsx:207,211`). None in
the patched file.

**Not done (follow-up for N):** `AnimationRegistry.build()` still swallows
the underlying error into `null`, so the notice says *what* failed but not
*why*. Surface the reason (fetch status / retarget error) so the console line
names it.

## Defect — Frontend: debug axis labels X/Y/Z render over chat + sidebar (P2)

**Symptom:** the red/green/blue X, Y, Z letters show through the chat box and
the sidebar on every laptop.

**Cause:** `CharacterViewer.tsx` draws the labels with drei `<Html>`, which are
DOM nodes, not WebGL. drei's default `zIndexRange` is `[16777271, 0]`; the
chat/sidebar sit at z-index 9999/9998 (`FloatingNavBar.tsx`), the logo at
9990, mobile chat at z-40. No wrapper between the labels and the page root
creates a stacking context, so the labels win. `ThinkingBubble.tsx:96`
already caps its own `<Html>` at `[100, 0]` — the axes were never given the
same. Compounded by `environmentConfig.ts` `debug.showAxes: true` with no
production guard, and `GraphicsContext` persists it to localStorage.

**Fix:**
- `CharacterViewer.tsx` — module const `AXIS_LABEL_Z = [100, 0]`, passed as
  `zIndexRange` on all three labels.
- `environmentConfig.ts` — `showAxes: false` by default. Developers flip it
  in Graphics settings; it persists per browser. `showGrid` untouched (WebGL,
  never overlapped anything).

**Verification:** `tsc --noEmit` 0 errors (after `npm install` restored the
i18n packages). `vitest run` 291/291. `eslint` on the three changed files: 0
errors, 1 pre-existing warning (`consumePreviousAvatar` dep, present before
the change). Not verified visually — app is behind Cognito; dev server left
running for N to sign in and confirm.

## Feature — Frontend: camera locks to the face during the `kiss` gesture

**Ask (Owner):** while the kiss plays, the user must not be able to rotate
the camera, and the camera must move to a close-up of the face from wherever
it currently is — including a manual (user-dragged) camera.

**Design:** new `CameraMode` `face`, granted only by the FSM, never pickable.

- `AnimationStates.ts` — `gesture.camera: 'face'`. Applies to every gesture,
  not only `kiss`; today `kiss` is the only gesture in any profile, and
  gestures are close-range reactions by nature. If a future gesture needs a
  wide shot, add a per-gesture camera field to `GestureDef` then.
- `CameraController.ts` — `onStateChanged` handles `face` BEFORE the manual
  check (the whole point is to override a user-held camera). Remembers
  `resumeMode`; on leaving the lock, `manual` is handed back (with its idle
  timer restarted), anything else falls through to the normal `head` rules.
  `notifyManualInteraction` and `setMode` are no-ops while locked; `setMode('face')`
  is refused always. `isLocked` getter.
- `CharacterViewer.tsx` — `face` preset `[0, 0.45, 0.04]` (tighter than
  `head`'s 0.5 and lifted to eye level); `<OrbitControls enabled={!locked}>`;
  `minDistance` dropped to 0.3 while locked, because the user's 1 m minimum
  would clamp the close-up back out (it already clamps `head` from 0.5 to 1.0,
  silently). The existing mode-change effect provides the 0.6 s eased move
  from wherever the camera is.
- `MotionControlPanel.tsx` — disabled "Face (locked by gesture)" option so
  the dev select is not blank mid-clip.

**Exit path is guaranteed:** `gesture` is `loop: once, onFinished: idle`, and
`idle` is reachable from anywhere, so every way out of `gesture` fires
`onStateChanged` and releases the lock.

**Verification:** 4 new `CameraController` tests (lock+release to head,
override manual and hand back, input/preset ignored while locked, lock
cancels a running hips cooldown). `vitest` 295/295, `tsc` 0 errors,
`eslint` clean on changed files. Framing numbers NOT visually tuned — app is
behind Cognito. N: click the mouth from a dragged-out camera and adjust
`CAMERA_RESPONSIVE_PRESETS.face` if the crop is off.

## Feature (cont.) — locked camera TRACKS the kissing hand

**Ask (Owner):** locked, but not static — the camera must move with the
hand. Consulted: Blender-authored camera vs code. **Decision: code.** A baked
camera path is per-rig (breaks on a taller/shorter VRM), needs a new
extraction+retarget path for cameras, forks a Mixamo asset, and ignores the
responsive mobile framing. The follow loop is already a per-frame bone
reader; pointing it at a second bone is the whole feature.

**Follow vs track:** chose **track** — camera position is held where the
entry transition parked it, only the look-at target moves. "Follow" would
translate the camera with the target, so the hand coming toward the lens
would push the camera away from it.

**Which hand:** measured, not guessed. Ran `Kiss.fbx` through three's
FBXLoader + AnimationMixer in Node and sampled hand→head distance:
left hand 76 → 31 cm (t≈1.9 s) → 76 cm; right hand stays 50–76 cm.
**Left hand.** Clip is 3.73 s.

**Implementation** (`CharacterViewer.tsx`):
- `CAMERA_MODES` entries are now `CameraModeDef { boneName, trackBone?,
  trackWeight?, holdPosition? }`. `face` = Head anchor, LeftHand track at
  weight 0.4, `holdPosition: true`. `head`/`hips`/`manual` unchanged.
- Follow loop computes `lookPos = lerp(anchor, trackBone, weight)` each
  frame. Entry transition parks the camera relative to the ANCHOR and aims
  at `lookPos`. In `holdPosition`, steady state damps `controls.target`
  toward `lookPos` with `1 - e^(-8·dt)` (frame-rate independent, ~0.5 s
  settle) and calls `update()` — no position delta. Runs BEFORE the
  `followTarget` config check: an FSM lock owns the camera.
- `FACE_LOCK_MIN_DISTANCE` 0.3 → 0.15: the blended target moves toward the
  lens during the blow; OrbitControls' radius clamp would otherwise shove
  the camera back.

**Known interaction:** dev-panel Lock X/Y/Z still reverts target motion on
locked axes during the gesture. Debug tool; left as is.

**Verification:** `tsc` 0, `eslint` clean, `vitest` 295/295. Not visually
tuned (Cognito). N: `trackWeight` and the `face` preset offset are the two
knobs; if the hand leads too hard, drop to 0.3.
