## Fix — Zoom-in stopped working (1 m floor, off-character orbit point)

**Report (Owner):** zoom-in stops working. A diagnosis from another session was reviewed against the code first.
- **Confirmed:**
  - The 1 m `minDistance` is the orbit-distance floor.
  - `zoomToCursor` was off.
  - A pan leaves the orbit point off the character (`followTarget: false` never re-pins it).
  - Lock Y blocks zoom.
- **Corrected:**
  - The env var is `VITE_API_GATEWAY_URL` (`VITE_API_BASE_URL` was removed on 21-08).
  - The 28-09 fix only masked the first gesture.
  - `zoomToCursor` keeps the distance floor.
  - Lowering `minDistance` also moves the head preset.

**Main cause:** the `head` preset is `[0, 0.5, 0]`. It only ever landed at 1 m because the transition and OrbitControls clamped it to the 1 m `minDistance`. So the default head view sat exactly on the zoom floor, and zooming in did nothing even without a pan.

**Change:**
- `CameraConfig.ts`: `minDistance` 1 → **0.5 m**.
- `CharacterViewer.tsx`:
  - The `head` wide preset is `[0, 1.0, 0]`, so the desktop default view is still 1 m; it no longer depends on the clamp.
  - OrbitControls gets `zoomToCursor`: zoom goes toward what is under the pointer, so zooming onto her works after a pan. three moves the orbit point with the zoom, and `onEnd` may count that as a pan → manual, as any real zoom already did.
  - First camera placement now snaps the responsive offset (and target Z) to the preset. Before, it placed the camera one smoothing step from the refs' initial `(0, 0.5, 0)` (~0.6 m), which the old 1 m clamp hid.
    - Side effect on mobile: the first view now uses the intended narrow framing (2 m, target lowered 0.6 m for the chat dock) instead of the clamped 1 m. Every later camera transition already landed there.

**Not changed:** the face lock (`FACE_LOCK_MIN_DISTANCE`), hips framing, and Lock X/Y/Z. Lock Y still blocks zoom by design.

**Checks:** tsc 0, eslint clean on the changed files, vitest 38 files / 415 tests pass. Not checked visually: the real viewer needs the catalog backend and Cognito.

## Audit — Mobile portrait / landscape responsiveness (report only, no code change)

**Method:** local dev server with `VITE_AUTH_DISABLED=true` (a temporary launch config, removed after). The character-load error overlay was hidden in the browser for inspection, since there was no backend. Viewports: 390×844, 667×375 and 844×390.

**Portrait (390×844): OK.**
- Logo top-left, rail right-centre, composer pinned at the bottom.
- The dock handles the keyboard through `visualViewport`.

**Landscape — problems found:**
1. **Small landscape phones (width < 768, e.g. 667×375), chat collapsed:**
   - The right rail (y 93–282) overlaps the composer dock (from y 245) by about 37 px. `chatRailTop` only lifts the rail above the dock when the chat is expanded.
   - Fix: always cap the rail's bottom at `dockTop − CHAT_RAIL_GAP` (use `dockBounds.top` even when collapsed).
2. **Same phones, chat expanded:**
   - The message list gets about 40 px (one row), because `chatHeightLimit` subtracts the rail's height, stacking the rail above the chat.
   - Fix: in landscape (`width > height`), let the rail sit beside the dock (shrink the dock's right margin by the rail width) and stop subtracting `railHeight`.
   - Or: use a side-by-side layout in landscape (chat as a left/right column, e.g. 45% width, full height).
3. **Most modern phones in landscape (width ≥ 768: 844, 915, 932) get the desktop layout** (`useMediaQuery('(max-width: 767px)')`), with the floating nav bar and hover-style panels on a ~390 px tall touch screen.
   - The chat panel fits (82vh cap).
   - **Non-chat panels have no height cap:** sessions measured 520 px on a 390 px screen, running ~146 px off the bottom.
   - The nav bar also sits over the ECA logo.
   - Fix: treat short touch screens as mobile — `(max-width: 767px), (max-height: 500px) and (pointer: coarse)`. Separately, add `max-h-[calc(100vh-2rem)]` to all desktop panel sizes (also helps short laptop windows).
4. **Code findings, not reproducible in emulation:**
   - `index.html`'s viewport meta has no `viewport-fit=cover`, so iOS reports `env(safe-area-inset-*)` as 0. The existing safe-area padding (dock, sheets, rail top inset) is inert, and in landscape the notch can cover the logo or rail. Fix: add `viewport-fit=cover`.
   - `<main className="h-screen">` uses 100vh, which on mobile browsers includes the area behind the address bar. Consider `h-dvh`.

Owner: report only ("tell what to change, do not apply").

## Fix — Landscape phone layout (audit items 1–3 applied)

**Owner:** "do 1 to 3 first". Items 4–5 (`viewport-fit=cover`, `h-dvh`) are left for a real-iPhone check.

1. **Rail never overlaps the dock** (`MobileChatLayout.tsx`): `chatRailTop` always gets `dockBounds.top` in portrait, closed dock too. Before, only an open dock lifted the rail. No change in normal portrait: the centred rail is already above the dock (verified 390×844, rail 328–517, dock from 548/714).
2. **Landscape: rail beside the dock, not above it.**
   - `isLandscape(innerWidth, innerHeight)` uses the layout viewport, so a keyboard cannot flip a portrait phone.
   - The dock gets `style.right = dockRightInset(railWidth)`.
   - `chatHeightLimit` no longer subtracts the rail's height, and the rail may use the full height.
   - 667×375, measured: dock right edge 599 vs rail left edge 607 (no overlap, closed or open). The message list is ~131 px, where it was ~40.
   - Helpers are in `lib/mobileChatLayout.ts` (+4 tests).
3. **Phone layout for short touch screens.**
   - `lib/layoutQuery.ts` `MOBILE_LAYOUT_QUERY = (max-width: 767px), (max-height: 500px) and (pointer: coarse)`, used by `FloatingNavBar`.
   - New Tailwind variant `desktop:` in `index.css`, its exact negation. It replaces `md:` in the components that pick the phone vs desktop layout: ChatPanel, ChatMessage, ChatInputBar, MobileChatDock (`desktop:hidden`), ChatDivider, MainLayout (music toggle), KofiButton. Without it, a sideways phone would get the mobile layout with the dock hidden by `md:hidden`.
   - Checked that the compiled `.desktop\:hidden` carries the right `@media`, and that the two queries were exact opposites at 844×390.
   - Other `md:` uses (modals, inputs, profile) were left as plain size tweaks.
   - **3b:** all desktop panel sizes get `max-h-[calc(100vh-2rem)]`; `shift({ padding: 16 })` keeps them on screen. 844×390 with a mouse: sessions 358 px (y 16–374), where it was 520 px running ~146 px off-screen. 1366×768: unchanged (520 px). Every panel already scrolls inside itself.

**Not verifiable in emulation:** a touch device at ≥768 px wide. The pane only emulates touch below 768 px, so at 844×390 it kept the (correct, mouse) desktop layout. The query logic was checked in the compiled CSS instead.

**Note:** while checking, `measure` looked like it never ran on load. That was the hidden Browser pane not rendering frames, so rAF and ResizeObserver don't fire. After one rendered frame it runs. Not an app bug.

**Checks:** tsc 0, eslint clean on the changed files, vitest 38 files / 419 tests pass. The temporary no-auth launch config was removed, and `.claude/launch.json` is back to its original.
