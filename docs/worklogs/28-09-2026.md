## Fix — Head/hips camera: first zoom-out snapped back into the head

**Report (Owner):** in head or hips mode, the first zoom-out past some distance zoomed back into the head; after that, zooming worked normally.

**Cause:**
1. A zoom (or pan) past `MANUAL_THRESHOLD_ZOOM` = 0.2 m makes OrbitControls `onEnd` call `notifyManualInteraction()`, which switches the camera to `manual`.
2. The camera-mode effect started the usual 0.6 s transition for that switch. Outside a face release its `endOffset` is null, so it flew to `followPos + preset` — the head framing — undoing the zoom.
3. After that the camera was already in `manual`, so later zooms stuck.

**Fix** (`CharacterViewer.tsx`, camera-mode effect):
- Entering `manual` from any mode except a `face` release runs no transition.
- It also cancels one in flight, so the user's own view stays put.
- The face-release hand-back to manual, and manual → head/hips (preset button, 2.5 min auto-return), still animate as before.

**Checks:** tsc 0, eslint clean on the changed files, vitest 36 files / 392 tests pass. Not checked visually, because the app is behind Cognito.

## Fix — Generated motion flipped the camera to manual

**Report (Owner):** whenever a motion played, the camera switched to manual. Wanted: head/hips stays automatic (the motion is framed on the hips); manual stays manual.

**Cause:** the only path into `manual` is OrbitControls `onEnd` → `notifyManualInteraction()`, which compares the target and distance at the start and end of a pointer gesture. During a motion (`exercise`, camera `hips`) two things move them without the user:
- ~~The follow loop re-pins `controls.target` to the walking hips every frame~~ **Correction (later the same day):** per-frame follow is off by design (`CameraConfig.followTarget: false`), so this was not a cause. The cause was the transition below.
- The head → hips (and later hips → head) transition moves target and distance by itself, so a gesture overlapping it measured as a "zoom".

**Fix** (`CharacterViewer.tsx`, `onStart`/`onEnd`):
- Pan counts only when the camera is not following (`followTarget` off, or already manual).
- A gesture that overlapped a camera transition is not measured: `transitionGenRef` is bumped per transition, and the gesture is skipped if a transition was active or started during it.
- A real zoom past 0.2 m still switches to manual, as before.
- Unchanged: `exercise` → `hips` framing, the 3 s cooldown back to `head`, and manual staying manual through a motion (`CameraController` returns early when manual).

**Checks:** tsc 0, eslint clean, vitest 392/392 pass. Not checked visually, because the app is behind Cognito.

## Fix — Back-to-back motions walked the character out of the hips framing

**Report (Owner):** "sometimes the zoom and focus break after doing some continuous movement". Check it, and change nothing if there is no problem.

**Finding:** there is a problem.
- Per-frame follow is off by design (`followTarget: false`, because re-pinning the target wipes a manual pan). The camera re-frames only on a camera-mode change.
- Motions played back to back stay in `hips` (exercise → exercise, or → idle → exercise within the 3 s cooldown), so no re-frame happens. Root motion accumulates across clips and the character leaves the shot.
- The next re-frame (the cooldown back to `head`) then jumps.

**Fix** (`CharacterViewer.tsx`, follow loop):
- While the mode is `hips`, camera **and** target are carried by the XY delta of the Hips bone, low-passed at `HIPS_FOLLOW_RATE` = 2/s.
- Adding the delta, instead of re-pinning the target, keeps the user's orbit, zoom and pan.
- In-place sway (lunges, squat weight shift) is damped; vertical bob is ignored.
- The baseline is reset during transitions and on "Reset position".
- Head, face and manual modes are unchanged.
- Manual detection: `onEnd` now subtracts the carry applied during the gesture (`followShiftRef`), so the character travelling never counts as a user pan. A real pan still counts. The earlier `following` condition (always false) is removed.

**Checks:** tsc 0, eslint clean, vitest 392/392 pass. Not checked visually, because the app is behind Cognito.

## Change — TTS sentence by sentence, whole reply spoken

**Request (Owner):** TTS is slow; synthesise sentence by sentence so the output starts sooner. Speak the full reply ("go full"), not only the first sentence.

**Where the delay was:** SpeechLLm already streamed audio (first piece ~0.4 s warm), but generation runs slower than playback (0.64–0.74× realtime). So the player waited silently before the first sound, to play the whole reply without a gap: about 0.56 × the reply's audio length, capped at 15 s. Separately, replies over 600 chars spoke only their first sentence.

**Change:**

Backend:
- `services/vieneu_tts/text_budget.py` rewritten: `split_sentences` / `plan_spoken_text` → `SpokenPlan(segments, truncated)`.
  - Splits at `. ! ? …` and newlines.
  - Guards: a decimal (`2.5`) and a list marker at the start of a line (`1.`) do not end a sentence; `…khoảng 10.` does.
  - Repeated marks and closing quotes stay with their sentence.
  - Pieces under 40 chars join the next one; pieces over 400 chars are cut at a word boundary.
  - No length cap by default. `TTS_MAX_SPOKEN_CHARS`, if set, keeps whole segments that fit.
- `api/main.py::_stream_speech` (shared by /chat and POST /tts): one `synthesize_stream` call per segment, in order, on the same open stream. To the browser it is still one clip:
  - one `speech_start`, with whole-reply totals plus `sentences`;
  - a new `speech_sentence {index, first_seq, estimated_audio_s}` before each sentence's chunks;
  - chunk `seq` continuing across sentences;
  - one `speech_end`.
- Failure before any audio → `speech_failed` (as before). Failure after some audio → `speech_end {partial: true}`: the audio plays but is not cached.

Frontend:
- `SpeechClip` records `sentences` and `partial` (`intact` is false when partial).
- `firstEstimate` = the first sentence's estimate, so the start-of-play buffer covers sentence 1 only.
- `speechSchedule.sentenceStartTime` + a `StartGate` on `ChunkScheduler`: while the clip is streaming, the chunk that opens sentence k≥1 waits for that sentence's own buffer (`priorStartTime` over its estimate, capped at 15 s).
  - No wait if the previous sentence is still sounding, or if a later sentence has already started arriving.
  - Waiting lands between sentences, not mid-word, and is not counted as `lateBy` starvation.
- Cache replay and older servers (no marks) behave as before.

**Simulated** (5 sentences × 4 s at 0.64×): first sound about 9 s sooner than whole-reply buffering, with no gap inside any sentence.

**Checks:**
- vitest 36 files / 403 tests pass; tsc 0; eslint clean on the changed files. There is one existing error in `speechPlayer.test.ts:171`, which this change did not touch.
- Backend (ECA conda env): `test_tts_text_budget.py` rewritten, `test_tts_spoken_cap.py` updated, and two `test_phase5_sse.py` tests updated to the new contract (a `speech_sentence` in the /tts event list; a stream cut after audio now ends with a partial `speech_end`, not `speech_failed`). TTS + SSE + streaming-client suites: 72 pass.
- `tests/infra/test_tts_route_infra.py` needs `aws_cdk`, which is not installed in the ECA env; not run.

**Watch (deploy):**
- The agent Lambda times out at 300 s. A very long reply spoken in full (~3,500+ chars ≈ 300 s of synthesis) would be cut mid-stream, and the browser then gets no `speech_end`.
- TTS is unhosted on the deployed agent today, so this only matters once it is hosted. The fix then is a time budget in `_stream_speech`: stop starting new sentences near the limit and send a partial `speech_end`.
