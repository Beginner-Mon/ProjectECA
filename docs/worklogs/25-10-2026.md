## E2 chat error handling

A failed turn now shows on screen, and can be sent again. Frontend only; E1 (backend `error` event) is already on the branch.

- `lib/chatErrors.ts` (pure): `ChatError`, `errorFromEvent` / `errorFromHttp` / `errorFromThrow`, and ONE table from code to wording (`errorCopy`). Persona lines (`error_system`, `error_stream`, `error_unavailable`) for what the user cannot fix; neutral i18n for `session_expired`, `rate_limited`, `bad_request`. An unknown backend code is worded like `provider_unavailable`.
- `lib/characterCopy.ts`: `error_system`, `error_unavailable` added to `UiStrings` with vi/en fallbacks. i18n: `chat.error_*`, `chat.retry`, `chat.sign_in_again`, `chat.open_llm_settings`, `chat.interrupted_note`.
- `lib/api.ts`: non-2xx throws `HttpStatusError(status)` (status logged, body never read); `consumeSSE` has a 45 s idle watchdog (`StreamTimeoutError`, any byte including pings resets it); `SessionMessage` has `error_code` / `interrupted`.
- `ChatContext`: handles the `error` event; `done` with no text and no error becomes `no_answer`; a cut stream keeps the text already shown and adds `interrupted` (it used to overwrite the bubble); recovery polling only for `interrupted` / `network`; unknown events go to `console.debug`. A stream cut AFTER `session_persisted` is not an error (the answer is saved and complete).
- Retry: `sendPrompt(text)` is the old `handleSend` body; the composer and "Thử lại" both call it. The prompt is kept in a ref keyed by assistant bubble id (restored bubbles use the user message before them). The question is saved a second time in history; accepted.
- History: `error_code` rows restore as an error bubble, `interrupted` rows as text plus a small note. Retry only on the newest assistant turn.
- `ChatMessage`: no more `return null` for an error or notice; one `ErrorBlock` for every code. A BYOK failure with ECA failing too (`provider_notice.answered_by` null) adds the "open key settings" link.
- Shell requests: `ChatContext.uiRequest` / `requestUi` (a counter, no new store). `FloatingNavBar` opens the chat dock on mobile when an error arrives, and opens Settings on Providers for "open key settings" (`ProfileSettingsModal.initialSettingsView`).
- Tests: `chatErrors.test.ts` (code table), `api.test.ts` (non-2xx, `error` event, done without text, watchdog with fake timers, cut stream), `characterCopy.test.ts`.

Checks in `ECA_UI/frontend`: `npm test` 57 files / 624 tests before, 58 / 680 after; `npm run lint` clean; `npm run build` ok.

## E3 silent error spots

Three places where a failure left the screen blank, saying "empty", or spinning. Frontend only.

- Conversation would not load (`switchToSession`, and a non-404 restore on page load): the chat panel now shows the shared error block (`ErrorNotice`, extracted from E2's `ErrorBlock`) with the persona `error_system` line and "Thử lại". The failed session stays selected; retry (`retrySessionLoad`) reloads it, and clicking it in the list again also retries. No greeting, no empty panel. A 404 on restore still drops the pointer and starts fresh. Decision in `lib/sessionLoad.ts` (`cancelled` / `missing` / `failed`).
- Session list (`refreshSessions`): `sessionsError` in context. The panel shows "Không tải được danh sách hội thoại." + "Thử lại" (key `sessions.load_failed`); "No sessions yet" only after a successful load with zero rows. If a refresh fails while an older list is on screen, the list stays with a one-line warning above it.
- First character load (`MotionContext`): only a 404 moves on to the next candidate; any other error sets `vrmOptionsError`. Logic in `lib/characterBoot.ts` (`resolveInitialCharacter`, unit-tested); `fetchCharacter` now carries `status` on its error. `LoadingOverlay` gained an error state (no spinner, button), "Thử lại" calls `retryInitialCharacter`. An empty catalog is also an error now.
- Tests: `characterBoot.test.ts`, `sessionLoad.test.ts`; i18n parity covers the new key.

Choices: a 404 on switching (not restoring) is shown as a load error, since the list will drop the gone session on refresh. Retry of a failed restore loads through the switch path, so the replay-picker motions of that restore are not re-registered.

Checks in `ECA_UI/frontend`: `npm test` 58 files / 680 tests before, 60 / 698 after; `npm run lint` clean; `npm run build` ok.
