# Worklog 14/09/2026 — Fix Lambda OOM on retrieval + Kimodo re-enable

## Defect #1 — Backend/Infra: `vva-agent` OOM on every `needs_retrieval=true` turn (P0)

**Symptom (prod 14/09 08:54-09:00):** 5/5 turns with `needs_retrieval=true` or `needs_motion=true` died with `REPORT ... Max Memory Used: 1024 MB Status: error Error Type: Runtime.OutOfMemory` after `retriever_complete`. Pure chat (`needs_retrieval=false, needs_motion=false`) succeeded (5-6s, 328 MB).

Example: `do a squat` (`5081f2f8`) `planner needs_retrieval=true needs_motion=true` -> `retriever_complete (1927 tokens, 2x kb_search)` -> 105s gap -> OOM. `yes` (`59dbed42`) same.

**Root cause hypothesis (not yet measured before fix):** `agent_stack.py:318-327` sized `memory=1024` assuming the agent "just waits on DeepSeek" (billed memory x wall-clock). That holds for chat, not for retrieval: the ONNX embedding model (`intfloat/multilingual-e5-small` 470 MB + `onnxruntime` 50 MB, baked in `agenticRAG/Dockerfile:136-137` `ENV EMBEDDING_BACKEND=onnx`) is held in memory alongside `kb_search` results and `AgentState.messages`. Cold-start Max hit 1024/1024.

**Fix #1:** Bump `infra/infra/agent_stack.py:327` `memory_size=1024 -> 2048` (commit this file). Hotfixed prod via `aws lambda update-function-configuration --function-name vva-agent --memory-size 2048` on 2026-09-14T10:08 UTC (no image rebuild). Re-measure `REPORT Max Memory Used` for next retrieval turn and consider 1536 if headroom is large. Alternative (move embedding out of Lambda) deferred pending measurement.

**Verification pending:** Send `do a squat` / `yes` again, expect `retriever_complete -> kimodo node_start (if needs_motion) -> synthesizer -> chat_complete` and `REPORT Max Memory Used` ~1200-1400. Kimodo worker `kimodo-cluster` task `ce5e89d81197421f8f32d32dbf052d5a` already `RUNNING` (`model loaded, recovered 0 abandoned job(s)` at 08:35 UTC) with `vva-motion-jobs` `queued=0` — queue side was healthy, agent side was the blocker.

**Cost:** +1GB x 20s x $0.0000167 = ~$0.00033/turn extra vs 1024. Still cheaper than 300s timeout billed after client disconnect.

## Defect #2 — Frontend: pointer stored too early (secondary)

**Symptom:** 404 on every reload for 2h after a stream dies before `session_persisted`.

**Cause:** Pointer saved at `send` instead of on `session_persisted` event. `turnLifecycle.ts` already handles that event. Also not cleared on 404 restore, so stale pointer costs 404 repeatedly.

**Fix #2 (to do):**
- Store pointer on `session_persisted` event (move `setItem` in `turnLifecycle.ts`).
- Clear pointer when restore on mount gets 404.
- Test: stream dies before `session_persisted`, then reload, assert no `GET /sessions/{id}` sent.

Fix #2 alone would hide the 404 but leave lost turns (defect #1), so must not replace #1.
