# Worklog 24/09/2026 — Local backend: motion turn killed the whole chat

Continues [[19-09-2026]] on `local-testing-improve` (not pushed).

## Defect — Backend: Kimodo node raised on unconfigured AWS, turn lost (P1)

**Symptom (local):** any message the planner marks `needs_motion=true`
crashed with `botocore.exceptions.NoRegionError: You must specify a region`
during task `kimodo`. User got no motion AND no text answer.

**Cause:**
- `nodes/kimodo.py` `_table()` called `boto3.resource("dynamodb")` then read
  `os.environ["MOTION_TABLE"]`. Dev machine has no AWS region, no credentials,
  no `MOTION_TABLE` — `.env.example` documents it as *unset locally* and
  promises "/chat answers without any of this". That promise held only for
  turns without motion.
- Nothing caught the exception: not the node, not `_stream_chat`'s
  `graph.astream` loop in `api/main.py`. `kimodo -> synthesizer` is a fixed
  edge, so the synthesizer never ran.
- The node already degraded to `unavailable` for a missing hash secret; the
  table and AWS path did not follow the same rule.

**Fix (`agenticRAG/langgraph_agents/nodes/kimodo.py`):**
- `_table()` returns `None` when `MOTION_TABLE` is unset, without touching
  boto3; the node returns `{"state": "unavailable"}`. The guard lives in
  `_table()` so the existing tests, which replace `_table` with a moto table
  and set no env, are unaffected.
- `kimodo_node` is now a thin wrapper around `_kimodo_node` that catches
  `BotoCoreError | ClientError` (no region, no credentials, throttle, 5xx)
  → logs `kimodo_aws_error` → `unavailable`. Only botocore errors are
  caught, so a real bug in the node still fails loudly.
- Production (Lambda) unaffected: `VvaAgentStack` sets every variable.

**Tests (`tests/langgraph_agents/test_kimodo_node.py`)**, written red first:
- `test_unavailable_when_motion_table_unset` — also asserts boto3 is never called.
- `test_unavailable_when_aws_client_cannot_be_built` — the exact local failure.
- `test_unavailable_when_dynamodb_call_fails_mid_node` — throttle on
  `queue_depth` after a live heartbeat. Stubs the jobs functions instead of
  using the moto `table` fixture.

3/3 pass. Full `tests/langgraph_agents -m unit`: baseline 632 passed /
34 errors; with change 635 passed / 34 errors (the same moto setup errors).
One earlier run with the change showed 1 failure that did not reproduce on
rerun (the suite's slow SSE timing tests, 14–15 s each); treated as flaky.
**Environment gap:** `moto` is not installed in the `ECA` conda env,
so every existing test using the `table` fixture errors at setup here
(`ModuleNotFoundError: moto`). Unrelated to this change; not installed
(package download needs Owner approval).

## Defect — Frontend: hair and skirt snap at the end of an exercise (P2)

**Symptom (Owner, confirmed):** loose hair / skirt whip at the moment an
exercise hands back to idle.

**Cause:** frame order in `CharacterViewer.tsx` `VRMCharacter` `useFrame`.
Hair/skirt are NOT animated by clips — clips drive humanoid bones only; loose
parts hang off secondary bones driven by VRM spring-bone physics inside
`vrm.update(delta)`, which integrates in WORLD space. `RootMotionAccumulator`
and `GroundClamp` wrote the model group's transform AFTER `vrm.update`, so the
physics saw every group move one frame late, as a jump the body never made.
At exercise end the clamp's lift falls as the pose stands back up (body
stationary in the world: hips rise locally, group lowers by the same amount),
so each frame the hair saw the body rise, then drop.

**Evidence:** vitest scratch simulation with three-vrm's real
`VRMSpringBoneJoint` — body rises 1 m locally while the clamp lowers the group
1 m over 30 frames (world-stationary):

| Order | Max hair swing |
| --- | --- |
| physics, then clamp (old) | 10.58° (frame 1) |
| clamp, then physics (new) | 0.00° |

Probe file deleted after the run; not committed.

**Fix:** `rootMotion.update` + `groundClamp.update` moved above
`vrm?.update(delta)`, after the avatar-controller tick. Safe: both read
NORMALIZED bones, which the mixer + inertializer have already written; the
Inertializer's own group XY write was already before `vrm.update`. Rule now in
the code comment: every group-transform write lands before `vrm.update`.

**Rejected:** spring-bone `center` = `vrm.scene`. The inertializer hands root
travel from hips-local to the group during a blend (world continuous, hips
local moves up to the full displacement) — in centre space the hair would see
that local move as real motion and swing harder.

**Verification:** `tsc` 0, `eslint` clean, `vitest` 315/315 (includes the
release tests pulled in today). Not viewed live (Cognito) — N: play an exercise
that sinks (e.g. `motion_b28e8284`) and watch the hand-back to idle.

**Not addressed:** spring bones are never `reset()` after a model switch; hair
may swing in from its previous state on the first frames. Separate, lower
priority.

## Defect — Frontend: camera snaps back the instant the kiss ends (P2)

**Symptom (Owner):** after the kiss the camera jumps straight back instead of
easing out of the close-up.

**Cause (two, both in `CharacterViewer.tsx` `Scene`):**
1. drei `<OrbitControls>` runs `if (controls.enabled) controls.update()` in
   its own `useFrame` at priority **-1**, before our camera loop. The lock
   released `enabled` and restored `minDistance` 0.15 → 1 m in the same
   render, so on the very next frame drei clamped the camera from the ~0.45 m
   close-up out to 1 m. The 0.6 s transition then fought that clamp every
   frame. Net effect: an instant snap.
2. Returning to a `manual` camera never transitioned at all: the follow loop
   `return`s early in manual, and the user's pre-kiss view was never saved.

Also a smaller pre-existing snap: every transition ended at the `head` preset
(0.5 m), inside the default 1 m minDistance, and was clamped out a frame later.

**Fix:**
- `releasing` React state (+ ref mirror). `cameraHeld = locked || releasing`
  now drives `enabled` and the relaxed `minDistance`, so drei stays hands-off
  until the ease-out finishes. Cleared when the release transition completes,
  and on any mode change that cannot start a transition (never left stuck).
- Release transition: `FACE_RELEASE_SEC = 1.2` with ease-in-out cubic (other
  mode switches keep 0.6 s ease-out).
- Pre-lock view saved relative to the head bone on entering `face` (not while
  still releasing a previous lock); a release into `manual` eases back to it,
  re-anchored to the current head position.
- Every transition's end point is pushed out to the destination's min
  distance, so it lands where OrbitControls will hold it.

**Verification:** `tsc` 0, `eslint` clean, `vitest` 315/315. Not viewed live
(Cognito). N: click the mouth from (a) the default camera and (b) a
dragged-out camera; both should glide back over ~1.2 s with no jump at either end.

  (default unchanged). Here: `$env:VVA_BACKEND_CONDA_ENV = "ECA"`.
- **Shadows "go wrong when the avatar goes far out".** Directional shadow is
  auto-fitted every frame (`lib/shadowFit.ts`) and is position-independent;
  a live `__shadow()` probe showed a healthy 1.18 m half-width box centred on
  the avatar. Not yet reproduced. Findings: root-motion offsets
  (`RootMotionAccumulator`, `Inertializer.groupAccum`) accumulate forever, so
  the avatar drifts further with every action; the contact-shadow wrapper is
  rotated `-π/2` while the model group is `+π/2`, which by the math aims
  drei's capture camera down into the floor (likely renders nothing; not
  verified visually). Need a screenshot + probe reading taken while broken.
